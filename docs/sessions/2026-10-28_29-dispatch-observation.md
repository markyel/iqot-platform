## 4. Отписка → пауза с нашего ящика / домена (64528bc, решение владельца)
- Поставщик отвечает конкретному ящику. Сигнал «отписка» → **пауза этого ящика** для поставщика на 7 дней; повторный
  сигнал на тот же наш почтовый домен → **пауза домена**; каждое повторение +7 дней (`EMAILS_UNSUBSCRIBE_PAUSE_STEP_DAYS`).
  Стопа на поставщика целиком нет. После паузы письма снова идут.
- Таблица `reports.supplier_sender_pauses` (scope mailbox/domain, `pause_key` `m:<id>` / `d:<домен>`, signals, paused_until),
  сервис `App\Services\Senders\SenderPauses` (`record`, `active`, `blocks`, `pairs`). Тест `tests/Unit/SenderPausesTest.php`.
- `SupplierUnsubscribeEscalator::apply` — только счётчики поставщика + `SenderPauses::record` (ящик ответа — по
  `email_messages.to_email`, иначе последний отправивший); `unsubscribe_until`/override/disable больше не ставит.
- Учитывают паузы: диспетчер (письма в очереди ждут конца паузы, «на паузе по отписке» в выводе), plan-day, CampaignPersister,
  VerificationMailer.
- 8 поставщиков старой схемы переведены; 392 их письма старше 7 дней отменены (бэкап
  `storage/app/backups/unsub-old-pending-20261028-0810.json`; заодно отменилось 229 строк в статусе error — можно вернуть
  из того же бэкапа).

## 8. Обход ящиков по наименьшей доле израсходованного лимита (20c7de0, 29.10, решение владельца)
Симптом: новые ящики eespc.ru #276/#277 (REG.RU) 29.10 до 16:46 МСК не отправили ни одного письма (по 8 в очереди с 08:40).
Причина: мониторинг дал им самых загруженных получателей (по 11–13 писем в день с разных ящиков), а диспетчер обходил ящики
по id — каждое освободившееся место у получателя забирал ящик с меньшим id. Теперь `DispatchPendingEmails::orderSenders`:
ящики ветки «ящик на батч» первыми, остальные — по возрастанию `(отправлено сегодня + в полёте) / daily_limit`, равные —
случайно. Тест `tests/Unit/DispatchSenderOrderTest.php`. Через 5 минут после выкладки ушло первое письмо с #277.
