# Сессия 30.10.2026: «ящик на батч» хуже? — нет; текст письма называл чужой товар

Продолжение `2026-10-28_29-dispatch-observation.md`. Всё ниже выкачено на прод (коммиты `22718a5`, `92a1333`,
`queue:restart`), тесты — 119 OK.

## 1. Ветка «ящик на батч» не хуже основной — врало сравнение в админке
Владелец видел в «Ход выполнения → Эксперимент», что у ветки результат хуже (10,4% ответов / 2,8% с ценой против
15,9% / 3,8%). Причина — в основную ветку попадали **именные заявки клиентов** (`email_batches.is_customer_request=1`,
источник `web`: персональный ящик от реальной организации клиента, 23,2% ответов / 6,0% с ценой), которых ветке не
достаётся по замыслу, и **все адресаты** основной ветки (ветка пишет всему пулу, основная — по капам и релевантности).

Честное сравнение — только общие адресаты (замер 30.10, ответ = входящее в беседе по паре батч×поставщик,
цена = `request_item_responses` по той же паре):

| | Ящик на батч: ответ / цена | Основная: ответ / цена |
|---|---|---|
| Заявки API с 16.10, 163–170 общих адресатов | 10,4–10,5% / 2,8–2,9% | 9,3–9,5% / 2,1% |
| Мониторинг, запросы КП пулу с 28.10, 207 адресатов | 14,8% / 1,9% | 14,0–14,2% / 1,0% |

Вывод: ветка вровень или чуть лучше; выборка мала (≈40 писем с ценой) — разница в пределах случайности.
Письма ветки — тот же генератор и шаблоны без номера запроса; дефектов текста ветки не найдено (сломанных тем,
пустых/запасных текстов нет). У 13 из 41 ящика ветки подпись только с именем — доля писем с телефоном/ИНН как в
основной (14% против 11%).

**Правка (`22718a5`)** — `ProgressDashboard::branchCompare`: две таблицы на вкладке эксперимента, обе по общим
адресатам: «Заявки» (без именных заявок клиентов и мониторинга) и «Мониторинг — запросы КП пулу» (основная ветка —
только письма из `mp_asks` kind=rfq, reason=pool; проверки цен с сайта дают 13,6% с ценой и ветке не достаются).
В заголовке — «общие адресаты: N из M». На проде считается ~8 с, кеш страницы 60 с.

## 2. Текст дня называл товар чужой позиции
Найдено по пути: письмо #266545 «Можете помочь с лифтовыми канатами?» — позиция плата индикации.
- **Механизм.** Текст письма — один на ящик × сутки × шаблон × цель × область (`CampaignBodyGenerator::reuseKey`).
  Модель (gpt-4o) иногда нарушает запрет и называет тип своей позиции. До волн мониторинга (~250 батчей мониторинга
  в день) это не проявлялось; с 28.10 (волны КП, ~4 000 батчей/день) такой текст уходил в ~30 писем по чужим позициям.
- **Масштаб (с 23.10):** 22 из 1 143 текстов, ~310 писем, все 28–30.10, все — мониторинг («по канатам» под кнопкой,
  «по трансформаторам» под шунтом, «подшипниковые узлы» под платой, «по индикатору» под тормозом…).
- **Правка (`92a1333`):** `CampaignBodyGenerator::namesProduct()` — текст, где есть слово из названия/бренда позиции
  (без общих слов и слов области) или известное название детали (`PRODUCT_NOUNS`), в кэш дня не кладётся, достаётся
  только своему батчу. На 1 143 реальных текстах: пойманы все 22 плохих + 16 тоже называющих товар/бренд, ложных
  срабатываний нет. Тест `tests/Unit/BodyNamesProductTest.php`.
- **Промпт (решение владельца 30.10):** «по кнопкам приказа» под одной кнопкой неестественно в любом случае — дублирует
  таблицу. Убраны разрешение «обозначить тип/назначение позиций» и требование «назвать, ЧТО запрашивается»; теперь:
  товар и его тип не называть, ссылаться на позицию («по этой позиции» / «по позициям из списка»), допустима только
  область в целом («по лифтовым запчастям»). Кэш текстов `bodygen:v3` (тексты 30.10 по старому промпту не берутся).
  Проба на проде (8 ящиков, gpt-4o): товар не назван ни в одном тексте.

## Открыто
- Модель иногда пишет во множественном числе при одной позиции («по списку», «по одной из них») — некритично,
  дожать промпт, если будет резать.
- Запасные тексты (`fallbackBody`, при сбое ИИ) говорят «по позициям» и при одной позиции — правятся в коде.
- 9 pending-писем со старым неверным текстом не пересобраны (`emails:rebody --batch=…` — по решению владельца).
- ИИ-прокси с локальной машины недоступен (пускает только IP прода) — живую генерацию проверять пробой на проде.
- Отдельно не измерено, влияет ли упоминание типа товара в тексте на отклик; оценить по `sent_at ≥ 31.10`.
