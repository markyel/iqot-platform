## 1. Зачем: два разных продукта под одной вывеской

| | **Разовая заявка (RFQ)** — текущий режим | **Мониторинг цен** — новый режим |
|---|---|---|
| Объём | 1–25 позиций, разово | 10–30 тыс. позиций, постоянно |
| Вопрос клиента | «Кто продаст это сейчас и почём?» | «Сколько это стоит на рынке, и как меняется?» |
| Источник цены | КП поставщика в ответ на письмо | Публичная цена на сайте (+ подтверждение) |
| Цикл | заявка → рассылка → КП → закрытие | непрерывное обновление по графику |
| Узкое место | ёмкость ящиков/получателей, ~8% отклик | поисковый бюджет, вежливость к сайтам, качество сопоставления |

**Факты по API-потоку (прод, 14.10.2026):** 3187 позиций в 656 заявках (≈5 на заявку), уникальных 2458, **28% повторяются** с медианой интервала **62 дня**. Главный API-клиент — сам LazyLift (`IqotApiService::createSubmission`). Это и есть мониторинг, нарезанный на мелкие RFQ: рассылка тут буксует (до цели ≥4 цен доходят 4,4% позиций, 56% без единой цены, отклик ≈8%) и при этом жжёт репутацию ящиков.

**Принцип:** текущий алгоритм (RFQ, план дня v2) остаётся **одной из ветвей**. Мониторинг — отдельный конвейер, который берёт из RFQ-ветви только то, что нужно (базу поставщиков, ящики, разбор ответов), и может **эскалировать** в неё позиции, для которых публичной цены нет.

## 2. Режимы

| Режим | Что делает | Когда пишем поставщику |
|---|---|---|
| **IQOT-Lite** | Ищет публичные цены на сайтах поставщиков, переобходит по графику. Цена = «на сайте», с флагом доверия источника. | Никогда. |
| **Гибридный** | Lite + **подтверждение**: найденные на сайте цены отправляем поставщику «подтвердите актуальность и пришлите КП»; по ответам формируем пул **доверенных** сайтов. Позиции из профиля поставщика, которых нет на его сайте, — запрашиваем в том же письме. | Новый/непроверенный сайт с ценами; периодическая переаттестация; запрос не найденного. |
| **RFQ-эскалация** (опция программы) | Позиции без публичной цены по истечении N дней уходят в текущую RFQ-ветвь (план дня v2). | По правилам RFQ. |

Режим выбирается на **программу** мониторинга; эскалация в RFQ — флаг программы.

## 3. Ключевая идея: глобальный граф «товар × продавец», клиентские программы поверх

Дорогое (поиск, обход, сопоставление, доверие к сайтам) делается **один раз для всех клиентов**. Клиентская программа — это список ссылок на канонические товары + свой график и бюджет.

```
monitoring_programs ──< program_items >── mp_products ──< mp_identifiers
                                              │
                                              └──< mp_listings >── mp_sites ── suppliers (reports)
                                                       │
                                                       └──< mp_price_observations
mp_sites ──< mp_confirmations ──< mp_confirmation_items
```

### 3.1 Таблицы (основная БД `iqot`, MySQL 8, локально)
Почему не `reports`: объём наблюдений (≈2–3 млн строк/год на программу 30 тыс.), нагрузка на запись и независимость от легаси-процедур Beget. С поставщиками связь логическая: `mp_sites.supplier_id → reports.suppliers.id` (int unsigned).

- **`monitoring_programs`**: `api_client_id`, `user_id`, `name`, `mode` (lite|hybrid), `refresh_days` (SLA свежести цены, напр. 14), `discovery_rate` (позиций/сутки на первичный поиск), `rfq_escalation_days` (null = выкл.), `status` (draft|ingesting|active|paused|archived), счётчики покрытия, `webhook_url`, бюджеты.
- **`program_items`**: `program_id`, `client_ref` (ключ клиента, уникален в программе), сырые поля клиента (`name`, `brand`, `article`, `unit`, `attributes`), `product_id`, `match_status` (pending|matched|ambiguous|rejected), `priority`, `last_priced_at`, `next_due_at`.
- **`mp_products`**: канонический товар: `brand_norm`, `name`, `product_type_id`/`domain_id` (таксономия IQOT), `unit_kind` (piece|meter|kg|set…), `search_state` (new|searching|found|not_found|exhausted), `last_search_at`, `next_search_at`.
- **`mp_identifiers`**: `product_id`, `kind` (oem|mpn|ean|client_ref|alias), `value`, `value_norm`, `brand_norm`. **Уникальность — `(kind, value_norm, brand_norm)`**, не `(kind, value_norm)` (урок CE: один артикул у разных брендов).
- **`mp_sites`** (профиль сайта поставщика): `domain` (registrable), `supplier_id`, `kind` (supplier|manufacturer|marketplace|aggregator|unknown), `publishes_prices`, `publishes_stock`, `has_structured_markup`, `search_url_template`, `sitemap_url`, `catalog_indexed_at`, `fetch_mode` (http|headless), `robots_ok`, `blocked_until`, `rate_limit_ms`, **`trust_state`** (unverified|probation|trusted|stock_only|in_stock_only|untrusted), `trust_score`, `trust_reviewed_at`, `next_confirmation_at`, статистика (ok/fail/suspicious за 30 дней).
- **`mp_listings`**: `product_id`, `site_id`, `url` + `url_hash` (канонизированный), `match_confidence`, `match_method` (oem_exact|oem_brand|llm_verified|manual), `price`, `currency`, `price_kind` (retail|from|wholesale_tier|on_request), `vat_included` (null=неизвестно), `unit` + `unit_qty` (цена за что), `availability` (in_stock|on_order|out_of_stock|unknown), `stock_qty`, `observed_at`, `checked_at`, `next_check_at`, `content_hash`, `etag`, `last_modified`, `status` (active|suspicious|gone|failed|mismatch), `fail_count`, `confirmed_price`, `confirmed_at`.
- **`mp_price_observations`**: история: `listing_id`, `price`, `currency`, `availability`, `method` (structured|llm|unchanged|confirmed|kp), `status` (ok|suspicious|gone|failed|soft404|mismatch), `note`, `observed_at`. **Сбои тоже пишем** (урок CE: без них не посчитать надёжность сайта).
- **`mp_confirmations`** (Гибрид): `site_id`, `supplier_id`, `sender_id`, `email_queue_id`/`message_id`, `token`, `status` (draft|sent|answered|expired), `outcome` (all_actual|stock_actual|in_stock_prices_actual|not_actual|partial|no_reply), `answered_at`.
- **`mp_confirmation_items`**: `confirmation_id`, `listing_id` или `product_id` (для «не найдено на сайте»), `site_price`, `kind` (verify|quote_request), ответ: `confirmed`, `quoted_price`, `quoted_availability`, `deviation_pct`.
- **`mp_budget_ledger`**: учёт расхода по дням и программам: `yandex_queries`, `fetches`, `headless_fetches`, `llm_calls`, `llm_usd` (с **правильной** ценой модели — урок CE: учёт был завышен ×5).

## 4. Конвейер

### 4.1 Приём номенклатуры
- API: `POST /monitoring/programs/{id}/items` — upsert по `client_ref`, до 5 тыс. позиций за вызов, **асинхронно** (джоб на чанк; ответ 202 + id импорта). Плюс загрузка Excel из кабинета. Удаление/пауза позиции — тем же upsert с `active=false`.
- Нормализация: `ArticleNormalizer` **с переводом похожих кириллица↔латиница (А/A, В/B, Е/E, К/K, М/M, Н/H, О/O, Р/P, С/C, Т/T, Х/X)** — в CE/LazyLift этого нет; числа (`parseNumber` из LazyLift); единица (шт/м/кг/компл).
- **Внутренние коды клиента — не артикул** (урок LazyLift: КСУ НСИ, УПП, МТР). Артикул — модель из наименования или явное поле.
- Сопоставление с каноническим товаром: `oem+brand` точно → `oem` без бренда при единственном кандидате → иначе новый товар. Без эмбеддингов на первом этапе (MySQL, нет pgvector); при необходимости — `EmbeddingStore` по узкому предфильтру, как в CE.
- Классификация `product_type`/`domain` — переиспользуем классификатор API (`ClientCategoryClassifierService`), нужна для выбора профильных поставщиков.

### 4.2 Поиск продавцов (discovery) — порядок «от дешёвого к дорогому»
Для товара в состоянии `new`/просроченного `not_found`, в пределах бюджета (§5):

1. **Индекс доверенных и известных сайтов.** Если у сайта известен `search_url_template` (поиск по сайту: `/search?q={article}`) или проиндексирован sitemap товаров — ищем артикул там, без Яндекса. Это главный рычаг масштаба: крупный дистрибьютор с 50 тыс. SKU индексируется один раз, дальше — сотни позиций без поиска.
2. **Профильные поставщики IQOT** (`supplier_product_types`/`supplier_domains` по `product_type`), у которых сайт `publishes_prices` — тот же поиск по сайту.
3. **Яндекс** (`YandexSearchClient`, уже есть): **1 запрос** `"<артикул>" <бренд> цена` (+ 2-й `"<артикул>" купить` только если первый пуст). Не 8, как в исследовании CE. Чёрный список маркетплейсов/соцсетей/агрегаторов (у CE список шире — взять его). Маркетплейсы — отдельный вопрос (§12).
4. Найденные URL → **обработка страницы** (4.3). Новый домен с ценой → создаётся `mp_sites` (unverified) и, если это поставщик, — связь с `suppliers` (через существующий `SupplierDiscoveryService` с доменным гейтом).

Итог по товару: `found` (≥1 активный листинг), `not_found` (повтор поиска через 30/60/90 дней — экспоненциально), `exhausted`.

### 4.3 Обработка страницы листинга
1. **Загрузка**: HTTP (`PageFetcher` из CE: robots, cp1251, ETag/If-Modified-Since — **подключить**, в CE не используется); если текст пуст/короче порога или сайт помечен `fetch_mode=headless` → `HeadlessPageRenderer` (у IQOT уже есть, у CE нет). Капча/403 → `blocked_until` домена.
2. **Сверка URL**: финальный URL после редиректов ≠ исходного и похож на категорию/главную → `soft404` (в CE не ловится).
3. **Извлечение цены**: `StructuredPriceExtractor` из CE (JSON-LD → microdata → OpenGraph) **с проверкой, что разметка про наш товар** (sku/mpn/name содержит артикул; в CE одиночный товар принимается без проверки) и `RUR→RUB`. Иначе — LLM (gpt-4o-mini) по промпту, объединяющему `PriceCheckPrompt` CE и правила LazyLift: цена за что (шт/м/компл), НДС, «от», оптовые уровни, «по запросу», доставка/МКАД/порог заказа — не цена (`isNonItemPriceEvidence`), старая зачёркнутая — не цена. **Не обрезать текст вслепую до 7000** — сначала вырезать окно вокруг артикула/названия (урок CE: цена ниже 7000 символов терялась); не выкидывать `<form>`/`product-header` целиком (риск CE: блок цены внутри формы «В корзину»).
4. **Проверка идентичности (главный источник ошибок).** Правила `CatalogMatchVerifier` LazyLift: другой тип детали — не он, даже при той же серии; другие параметры (размер, левый/правый) — не он; при недостатке данных — не он. Плюс:
   - артикул — **точное** совпадение по токену, не подстрока (`ABC123` ⊄ `ABC1234`, урок CE);
   - бренд **штрафует** при явном расхождении (урок LazyLift: бренд только повышал score — «кнопка Thyssen» = «кнопка ASY»);
   - числовые признаки названия (`ItemNameSignals`: D=240 ≠ D=320);
   - «код серии» из названия не считается артикулом (урок LazyLift ECO3000);
   - аналог (другой производитель) — **не листинг** нашего товара; отдельная пометка `analog_of`, в цену не идёт.
   - Всё, что не прошло точное совпадение артикул+бренд, проходит LLM-проверку (урок LazyLift: в «серой зоне» 95% привязок были чужими).
5. **Санитарные проверки**: выброс ×4 от медианы при ≥4 ценах → `suspicious` (храним в БД, не считаем на лету, как CE); для 1–3 цен — сравнение с ценой КП из RFQ-истории IQOT (у нас она есть — `request_item_responses`!) и с предыдущей ценой листинга; скачок ×3 — только с повтором, но **повтор через 1–2 дня, а не через цикл** (в CE подтверждение занимало 28 дней).

### 4.4 Профиль сайта
Накопительно по домену: доля листингов с ценой/наличием, наличие разметки, `fetch_mode`, стабильность (fail/soft404/suspicious за 30 дней), **шаблон поиска по сайту** (обнаруживаем по форме `<form role=search>`/`action=` или пробным запросом известного артикула), sitemap товаров. Профиль решает: можно ли искать на сайте без Яндекса, нужен ли headless, какая вежливость.

### 4.5 Переобход (monitoring)
- Планировщик берёт листинги с `next_check_at <= now` в пределах бюджета и **лимита на домен** (атомарный токен-бакет на домен; в CE — `usleep` и неатомарно, блокирует воркер). Отдельная очередь `monitor`, свои воркеры.
- Каденция листинга: `refresh_days` программы, **сдвинутая доверием и волатильностью**: доверенный стабильный сайт — реже (до 2×), волатильный/подозрительный — чаще.
- Порядок: условный GET (304 → `unchanged`) → хеш **нормализованного блока товара** (а не всей страницы — счётчики/«похожие товары» ломают хеш) → разметка → LLM.
- Цена исчезла (стало «по запросу») — **цену не держим старой** (в CE держалась): `price=null`, `price_kind=on_request`, наблюдение пишется.
- Сбой — пишется в историю, `fail_count++`, повтор с отсрочкой (1 ч → 6 ч → 1 д), после N подряд — `failed` и повторный поиск товара на этом сайте.
- 404/410/`soft404` → `gone`, товар уходит в повторный поиск, если листингов не осталось.

### 4.6 Доверие к сайту и Гибридное подтверждение
**Состояния `mp_sites.trust_state`:**

| Состояние | Как попадаем | Что значит для цены |
|---|---|---|
| `unverified` | новый сайт с ценами | «цена с сайта, не подтверждена» |
| `probation` | отправлен запрос подтверждения | то же |
| `trusted` | ответ «Все цены актуальны» **и** выборочная сверка: цены КП/подтверждения совпали с сайтом (≤ X% расхождения) | «подтверждённый источник»; переобход сайта без писем |
| `stock_only` | «Актуальна информация о наличии» | наличие — доверяем, цену — нет (нужен КП) |
| `in_stock_only` | «Актуальны цены только на товары в наличии» | цена доверенная только у `in_stock` |
| `untrusted` | «не актуально» / систематические расхождения / молчание после N запросов | цена на сайте — справочно, КП обязателен |

**Письмо подтверждения (Гибрид)** — одно письмо на поставщика, **сводя позиции всех программ** (не дёргаем поставщика по каждой программе):
- «Мы нашли на вашем сайте эти позиции: [таблица: позиция, артикул, ссылка, цена с сайта, наличие]. Подтвердите актуальность и пришлите КП.»
- Кнопки-ссылки в один клик (токен, без логина — паттерн `SupplierResponseController` LazyLift): **«Все цены актуальны» / «Актуальна информация о наличии» / «Актуальны цены только на товары в наличии» / «Цены неактуальны — пришлю КП»**. Ответ письмом с КП разбирается существующим AI-анализом IQOT (`SupplierReplyAnalyzer`, промпт — с правилами единиц/аналогов LazyLift).
- Блок «**Позиции, которых нет на вашем сайте**» — профильная номенклатура из программ, не найденная у них: «есть ли у вас, по какой цене» (это и есть запрос не найденного).
- Отправка — через инфраструктуру IQOT (ящики, прогрев, пейсинг, анти-фингерпринтинг), отдельный шаблон и тон; учёт в общих капах получателя (§5 плана дня — не больше N писем получателю в день).

**Правила «лишний раз не дёргаем»:** не больше 1 письма подтверждения сайту в 30 дней; доверенный сайт — переаттестация раз в 90–180 дней или при аномалиях (расхождение с медианой, резкое изменение многих цен); запрос не найденного — пачкой, не чаще раза в 30 дней.

**Объективная сверка доверия** (не только слово поставщика): если по позиции есть КП (из Гибрида или из RFQ-истории IQOT) — сравниваем с ценой сайта на ту же дату; систематическое расхождение > X% → понижение доверия, независимо от кнопки.

### 4.7 Результат для клиента
По каждой позиции программы: лучшая цена (только из `trusted`/`in_stock_only`+наличие, либо с пометкой «не подтверждено»), медиана, все источники (сайт, цена, за что, НДС, наличие, дата, уровень доверия, ссылка), тренд (медиана изменений по продавцам — `PriceHistory` CE), свежесть. Плюс лента изменений.

## 5. Скорость и бюджеты

Регулятор (`MonitoringGovernor`) раздаёт суточные квоты: Яндекс-запросы, загрузки (HTTP/headless отдельно), LLM ($), письма подтверждения — по программам пропорционально `discovery_rate` и приоритету. Квоты — в `mp_budget_ledger`, атомарно.

**Оценка для программы 30 тыс. позиций** (порядки величин, уточнить на пилоте):
- Первичный поиск: ~1,3 запроса/позицию → ~40 тыс. запросов Яндекса. При 2 000/сутки (текущий потолок) — ~20 дней; с индексом крупных сайтов (§4.2 п.1) — заметно меньше. **Тариф Яндекс Search API уточнить** — это главная статья расходов первичного поиска.
- Переобход: при ~3 листингах на позицию ≈ 90 тыс. листингов; при `refresh_days=14` ≈ 6,5 тыс. загрузок/сутки. С условным GET/хешем/разметкой LLM нужен ~на 20–30% → 1,5–2 тыс. вызовов gpt-4o-mini/сутки ≈ $1/сутки (по замеру CE ≈ $0,0005 за проверку).
- Headless (Chrome) — дорогой по памяти (сервер 7 ГБ): только для сайтов с `fetch_mode=headless`, отдельный пул из 1–2 воркеров.
- Вежливость: ≤1 запрос/с на домен по умолчанию; крупный дистрибьютор с 5 тыс. листингов × раз в 14 дней ≈ 360 загрузок/сутки — укладывается.

## 6. Связь с текущим IQOT

| Используем из IQOT | Как |
|---|---|
| `suppliers` + доменный гейт дискавери | новые сайты-поставщики заводятся тем же путём; `mp_sites.supplier_id` |
| Таксономия и классификатор API | профильные поставщики для позиции |

## 7. Новый API (черновик контракта)
- `POST /api/v1/monitoring/programs` — создать программу (mode, refresh_days, discovery_rate, rfq_escalation_days, webhook_url).
- `POST /api/v1/monitoring/programs/{id}/items` — upsert пачки (≤5 тыс.), 202 + `import_id`; `GET …/imports/{id}` — прогресс.
- `GET /api/v1/monitoring/programs/{id}` — статус, покрытие (найдено/не найдено/в поиске), свежесть, расход.
- `GET /api/v1/monitoring/programs/{id}/prices?updated_since=…&cursor=…` — изменения цен курсором (основной способ синхронизации).
- `GET /api/v1/monitoring/programs/{id}/items/{client_ref}` — источники и история.
- Вебхуки (HMAC-подпись): `price.changed`, `item.found`, `item.not_found`, `program.coverage` (порог).
- Экспорт Excel из кабинета.
LazyLift — первый потребитель: заменяет поток мелких RFQ на программу мониторинга своего каталога и берёт цены курсором.

## 8. Уроки CE и LazyLift → обязательные правила
1. Цена доставки/МКАД/порога заказа — не цена товара; цитату-доказательство храним.
2. Артикул сопоставляем по токену, с переводом похожих букв; не подстрокой.
3. Бренд при явном расхождении — штраф/отказ.
4. Серая зона сопоставления — только через LLM-проверку; аналог ≠ наш товар.
5. Единица цены (шт/м/компл) и НДС — обязательные поля; неизвестно = null, не «шт» и не «с НДС».
6. Нет цены сейчас → не держим старую.
7. Сбои пишем; мягкий 404 ловим по редиректу и тексту.
8. Скачок цены — повтор через 1–2 дня, не через цикл.
9. Выбросы — флаг в БД, и для 1–3 цен — сверка с КП-историей.
10. Учёт стоимости LLM — по точному имени модели; стоимость поиска — тоже в учёт.
11. Повторный LLM-разбор недетерминирован: результат, прошедший проверку, не перезаписываем без причины.
12. Ответ поставщика по подтверждению сопоставляем только с позициями этого письма (урок LazyLift: иначе «одна цена на всё» размножается).

## 9. Фазы
- **Ф0. Фундамент** (без писем): схема, приём номенклатуры (API + Excel), нормализация, канонические товары, регулятор бюджетов, перенос загрузчика/извлечения/монитора из CE с правками §8.
- **Ф1. IQOT-Lite на пилоте**: программа = каталог LazyLift (или его часть); поиск через Яндекс, листинги, переобход, выдача цен курсором. Метрики: покрытие, точность сопоставления (ручная выборка), стоимость/позицию.
- **Ф2. Профили сайтов**: шаблоны поиска по сайту, sitemap, индекс крупных сайтов → падение расхода Яндекса.
- **Ф3. Гибрид**: письма подтверждения, кнопки, состояния доверия, объективная сверка, запрос не найденного.
- **Ф4. API/вебхуки/кабинет/биллинг** для внешних клиентов.
- **Ф5. RFQ-эскалация** позиций без публичной цены в план дня v2.

## 10. Риски
- **Качество сопоставления** на 30 тыс. позиций — главный риск продукта (опыт LazyLift: 95% ошибок в серой зоне). Без выборочного контроля качества запускать нельзя.
- **Юридика и вежливость**: robots.txt и лимит на домен соблюдаем, UA браузера (решение §11); капчи не обходим.
- **Антибот/JS-цены**: headless помогает, но дорог по памяти.
- **Ёмкость писем** (Гибрид): конкурирует с RFQ за ящики и капы получателей.
- **Диск** на app-сервере (свободно 11 ГБ): сырые страницы не храним, только хеши/выдержки.
