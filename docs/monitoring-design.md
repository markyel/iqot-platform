# Дизайн: режимы получения цен (Основной / Lite / Гибрид) и Мониторинг

## 1. Две независимые оси

Цель везде одна — **актуальные цены**. Различаются (а) что за задача и (б) откуда берём цену.

### 1.1 Тип задачи
| | **Заявка** | **Мониторинг** |
|---|---|---|
| Объём | 1–25 позиций | 10–30 тыс. позиций |
| Жизнь | собрали предложения → консолидировали в отчёт → **закрыли** | **регулярно** (раз в 10–30–60–90 дней) обновляем цены по всему списку, задача не закрывается |
| Результат | отчёт по заявке | всегда актуальный прайс по списку + история и тренд |

### 1.2 Способ получения цены (режим)
| Режим | Как получаем цену |
|---|---|
| **IQOT — Основной** (текущий) | Запрос КП почтой: делим позиции на небольшие группы, рассылаем профильным поставщикам, разбираем КП / счёт / текст письма, консолидируем. |
| **IQOT-Lite** | Только сайты: ищем поставщиков, анализируем их сайты, извлекаем цены, сопоставляем с позициями, консолидируем. Писем нет. |
| **Гибрид** | Сайты + почта. По каждой тематической группе определяем пул поставщиков; у кого сайт с ценами — берём цены с сайта и **выборочно** перепроверяем запросом КП, накапливая доверие к сайту; **чем выше доверие — тем реже пишем**. У кого цен на сайте нет или доверие низкое — обычный запрос КП почтой. Итог: **больше цен при меньшем числе писем**. |

### 1.3 Сочетания
| | Основной | Lite | Гибрид |
|---|---|---|---|
| **Заявка** | текущий конвейер (план дня v2) | быстрый «рыночный» ответ по заявке с сайтов | заявка, где часть цен берём с доверенных сайтов, остальное — КП |
| **Мониторинг** | периодический RFQ — дорого, редкая каденция | дешёвый регулярный мониторинг сайтов | **целевой режим для больших списков** |

**Факты по API-потоку (прод, 14.10.2026):** 3187 позиций в 656 заявках (≈5 на заявку), уникальных 2458, 28% повторяются с медианой интервала 62 дня. Главный API-клиент — сам LazyLift. Это мониторинг, нарезанный на мелкие заявки в Основном режиме: до цели ≥4 цен доходят 4,4% позиций, 56% без единой цены, отклик ≈8%, ящики выгорают.

Текущий алгоритм (Основной, план дня v2) **остаётся** — он и есть почтовый канал, которым пользуется Гибрид.

## 2. Гибрид: как это работает

### 2.1 Канал на пару «поставщик × позиция»
Для позиции из тематической группы (product_type × domain) берём пул профильных поставщиков (селектор IQOT + discovery) и для каждого определяем канал:

| Сайт поставщика | Доверие | Канал | Что видит клиент |
|---|---|---|---|
| есть, с ценой на позицию | высокое | **сайт**; изредка — проверочный КП (по частоте выборки) | цена «с сайта, подтверждённого источника» |
| есть, с ценой | неизвестное / низкое | **сайт + проверочный КП** на выборку позиций | цена «с сайта, не подтверждена», после КП — цена КП |
| есть, но позиции/цены нет | любое | **КП почтой** (как в Основном) | цена из КП |
| нет сайта / сайт закрыт (капча, JS, 403) | — | **КП почтой** | цена из КП |

### 2.2 Проверочный запрос (верификация)
- Это обычный запрос КП, только на позиции, **найденные на сайте этого поставщика**, с указанием увиденной цены: «На вашем сайте позиция X — 12 400 ₽, в наличии. Подтвердите актуальность и пришлите КП». Письма — **дробные**, как в Основном (1–4 позиции в письме, адаптивный размер), через те же ящики, капы получателя, пейсинг и анти-фингерпринтинг.
- Ответ разбирает существующий AI-анализ (КП/счёт/текст). Для каждой проверенной позиции фиксируем **сверку**: цена КП vs цена сайта на ту же дату, совпадение наличия.
- Сверка **совпала**, если |КП − сайт| / сайт ≤ X% (с учётом НДС и единицы) и наличие не противоречит. Иначе — расхождение. Нет ответа — сверка не засчитывается ни в плюс, ни в минус (но считается для «молчит» → поставщик уходит в почтовый канал по общим правилам RFQ).
- Если поставщик пишет словами «цены на сайте актуальны только для товаров в наличии» / «наличие актуально, цены нет» — AI извлекает это как **заявление об области доверия**; оно влияет на область доверия (2.3), но уровень доверия всё равно определяют сверки.

### 2.3 Доверие к сайту: уровень и частота выборки
Доверие — по сайту (домену поставщика), накапливается из сверок.

| Уровень | Частота выборки (сколько найденных позиций проверяем КП) | Как попасть |
|---|---|---|
| 0 — новый | первая проверка на 3–5 позициях | сайт впервые дал цены |
| 1 | 1 из 10 | ≥N совпавших сверок, расхождений нет |
| 2 | 1 из 50 | ещё ≥N подряд совпавших |
| 3 | 1 из 100 | ещё ≥N подряд совпавших |
| вниз | расхождение → минус 2 уровня (или сразу 0 при 2 расхождениях подряд) | |

- «1 из 10» — от объёма **найденных и обновлённых на сайте** позиций этого поставщика за цикл; минимум — 1 проверка за T дней даже на верхнем уровне (свежесть доверия).
- Какие позиции брать в выборку: где цена на сайте изменилась, дорогие, давно не проверенные, случайные — смесь.
- **Область доверия** (из сверок и заявлений): `all` (цены и наличие), `in_stock` (цены верны только у позиций «в наличии»), `availability` (верно только наличие). Позиция вне области доверия — цена сайта показывается как неподтверждённая и запрашивается КП по обычным правилам.
- Объективная сверка работает и без писем Гибрида: если по позиции пришло КП в Основном режиме (любая заявка IQOT), оно тоже сверяется с сайтом — доверие копится «бесплатно».

### 2.4 Каденция в мониторинге
- У позиции программы есть **целевая свежесть** (например, 30 дней).
- Цена с сайта обходится **чаще** (дёшево: условный GET, разметка, без писем) — напр. раз в 10–14 дней.
- Цена, доступная только через КП, обновляется **реже** (60–90 дней), в пределах почтовой ёмкости.
- Проверочные КП — по частоте выборки уровня доверия, а не по каденции позиции.

## 3. Глобальный граф «товар × сайт» и задачи поверх

Поиск, обход, сопоставление и доверие делаются **один раз для всех клиентов**; заявка или программа мониторинга ссылаются на канонические товары.

```
monitoring_programs ──< program_items >──┐
reports.requests ──< reports.request_items ──(product_id)──┤
                                         mp_products ──< mp_identifiers
                                              └──< mp_listings >── mp_sites ── reports.suppliers
                                                       └──< mp_price_observations
mp_sites ──< mp_verifications >── mp_listings      (сверки КП↔сайт)
```

### 3.1 Таблицы (основная БД `iqot`, MySQL 8)
Не в `reports`: объём наблюдений (≈2–3 млн строк/год на 30 тыс. позиций) и независимость от легаси-процедур Beget. Связи с `reports` — логические по id.

- **`monitoring_programs`**: `api_client_id`, `user_id`, `name`, `price_mode` (lite|hybrid|rfq), `refresh_days` (целевая свежесть), `site_refresh_days`, `email_refresh_days`, `discovery_rate` (позиций/сутки на первичный поиск), `status`, счётчики покрытия, `webhook_url`, бюджеты.
- **`program_items`**: `program_id`, `client_ref` (уникален в программе), сырые поля клиента, `product_id`, `match_status`, `priority`, `last_priced_at`, `price_source` (site|kp), `next_due_at`.
- Заявке в режиме Lite/Гибрид: `reports.requests.price_mode` (rfq по умолчанию) + `request_items.mp_product_id`.
- **`mp_products`**: канонический товар: `brand_norm`, `name`, `product_type_id`/`domain_id`, `unit_kind`, `search_state` (new|searching|found|not_found|exhausted), `next_search_at`.
- **`mp_identifiers`**: `kind` (oem|mpn|ean|alias), `value`, `value_norm`, `brand_norm`; уникальность `(kind, value_norm, brand_norm)` (урок CE: один артикул у разных брендов).
- **`mp_sites`**: `domain`, `supplier_id`, `kind` (supplier|manufacturer|unknown), `publishes_prices`, `publishes_stock`, `has_structured_markup`, `search_url_template`, `sitemap_url`, `fetch_mode` (http|headless), `blocked_until`, `rate_limit_ms`, **доверие**: `trust_level` (0–3), `trust_scope` (all|in_stock|availability|none), `sample_every` (1/10/50/100), `verified_ok`, `verified_mismatch`, `consecutive_ok`, `last_verified_at`, `next_verification_due_at`, статистика обхода (ok/fail/soft404/suspicious за 30 дней).
- **`mp_listings`**: `product_id`, `site_id`, `url`/`url_hash`, `match_confidence`, `match_method`, `price`, `currency`, `price_kind` (retail|from|wholesale_tier|on_request), `vat_included`, `unit`/`unit_qty`, `availability`, `stock_qty`, `observed_at`, `checked_at`, `next_check_at`, `content_hash`, `etag`, `last_modified`, `status` (active|suspicious|gone|failed|mismatch), `fail_count`, `last_verified_at`, `last_verified_result`.
- **`mp_price_observations`**: история цен листинга, включая сбои: `method` (structured|llm|unchanged|kp), `status` (ok|suspicious|gone|failed|soft404).
- **`mp_verifications`**: сверка: `site_id`, `listing_id`, `site_price`, `site_availability`, `site_observed_at`, `kp_price`, `kp_availability`, `kp_source` (verify_ask|rfq — КП из обычной заявки тоже сверяем), `email_queue_id`/`request_item_response_id`, `deviation_pct`, `result` (match|mismatch|no_reply|scope_only), `scope_statement` (из текста ответа).
- **`mp_asks`**: «что нужно спросить почтой» — пары поставщик × позиции с причиной (`verify` | `rfq_no_site_price` | `rfq_low_trust`) и сроком; это вход почтового канала (§4.6).
- **`mp_budget_ledger`**: расход по дням и программам (Яндекс, загрузки, headless, LLM $ по **точной** цене модели, письма).

## 4. Конвейер

### 4.1 Приём номенклатуры
- `POST /monitoring/programs/{id}/items` — upsert по `client_ref`, до 5 тыс. за вызов, асинхронно (202 + `import_id`); загрузка Excel из кабинета.
- Нормализация артикула **с переводом похожих букв кириллица↔латиница** (нет ни в CE, ни в LazyLift); внутренние коды клиента (КСУ НСИ, УПП, МТР) — не артикул; числа и единица.
- Канонический товар: `oem+brand` → `oem` при единственном кандидате → новый товар.
- Классификация `product_type`/`domain` — классификатором API IQOT (нужна для тематических пулов).

### 4.2 Пул поставщиков по тематической группе
Для группы (product_type × domain): профильные поставщики IQOT (селектор + карма) + новые из поиска. По каждому поставщику — профиль сайта (`mp_sites`): есть ли цены, разметка, поиск по сайту. Пул едины для Lite, Гибрида и Основного.

### 4.3 Поиск листингов — от дешёвого к дорогому
1. **Поиск по сайту** известных поставщиков пула (`search_url_template` или sitemap) — без Яндекса. Главный рычаг масштаба: крупный сайт индексируется один раз.
2. **Яндекс**: 1 запрос `"<артикул>" <бренд> цена` (2-й — `"<артикул>" купить`, только если пусто). Чёрный список маркетплейсов, соцсетей, агрегаторов (§11).
3. Новый домен с ценами → `mp_sites` (уровень доверия 0) и, если это поставщик, — в `suppliers` через существующий discovery с доменным гейтом.
Товар без листингов → `not_found`, повтор через 30/60/90 дней; в Гибриде — сразу в почтовый канал (`mp_asks` rfq_no_site_price).

### 4.4 Обработка страницы листинга
1. Загрузка: HTTP с ETag/If-Modified-Since → headless, если пусто или сайт помечен; вежливо (robots, лимит на домен), UA браузера (§11); капча/403 → `blocked_until`, поставщик уходит в почтовый канал.
2. Финальный URL после редиректа — проверка на мягкий 404.
3. Цена: разметка (JSON-LD → microdata → OpenGraph) **с проверкой, что разметка про наш товар**; иначе gpt-4o-mini по окну текста вокруг артикула (не первые 7000 символов). Извлекаем цену, **за что** (шт/м/компл), НДС, «от», оптовые уровни, «по запросу», наличие. Доставка/МКАД/порог заказа — не цена.
4. **Идентичность** (главный риск): артикул — точный токен, не подстрока; бренд при расхождении — отказ; числовые признаки названия; код серии ≠ артикул; аналог ≠ наш товар; всё не-точное — через LLM-проверку (правила `CatalogMatchVerifier` LazyLift).
5. Санитария: выброс ×4 от медианы (флаг в БД); для 1–3 цен — сравнение с КП-историей IQOT; скачок ×3 — повтор через 1–2 дня.

### 4.5 Переобход
Очередь `monitor` со своими воркерами; атомарный лимит на домен; каденция = `site_refresh_days` с поправкой на доверие и волатильность; условный GET → хеш блока товара → разметка → LLM; цена пропала — не держим старую; сбои пишем, повтор с отсрочкой; 404/мягкий 404 → `gone` → повторный поиск товара.

### 4.6 Почтовый канал (общий с Основным режимом)
Гибрид и мониторинг не шлют писем сами — они **копят `mp_asks`** (поставщик × позиции × причина × срок). Отправляет их **план дня v2** как ещё один источник спроса, наравне с позициями заявок:
- те же конверты (1–4 позиции, адаптивный K), ящики, капы получателя (5–15 писем в день), ротация, анти-фингерпринтинг;
- приоритет в плане: заявки клиентов → проверочные КП (дёшево и копят доверие) → RFQ мониторинга по сроку свежести;
- отдельный шаблон для проверочного письма («нашли на вашем сайте … по цене …, подтвердите и пришлите КП»);
- ответ разбирает существующий AI-анализ; результат: цена позиции (в `mp_listings`/`program_items`) + сверка (`mp_verifications`) для `verify`.

Так один почтовый движок обслуживает все режимы, и мониторинг не выжигает ящики в обход капов.

### 4.7 Результат
По позиции: лучшая цена (с отметкой источника: сайт подтверждённый / сайт неподтверждённый / КП), медиана, все источники (поставщик, цена, за что, НДС, наличие, дата, доверие, ссылка), тренд, свежесть; лента изменений.

## 5. Скорость и бюджеты
Регулятор раздаёт суточные квоты: Яндекс-запросы, загрузки (HTTP/headless), LLM ($), **письма** (через капы плана дня) — по программам пропорционально `discovery_rate` и приоритету.

Оценка для 30 тыс. позиций (порядок величин, уточнить на пилоте):
- Первичный поиск: ~1,3 запроса/позицию ≈ 40 тыс. запросов Яндекса; при текущем потолке 2000/сутки ≈ 20 дней, с поиском по сайтам — меньше. **Тариф Yandex Search API — уточнить.**
- Переобход: ~90 тыс. листингов при `site_refresh_days=14` ≈ 6,5 тыс. загрузок/сутки, LLM на 20–30% ≈ $1/сутки.
- Письма: проверочные КП падают с ростом доверия (уровень 3 — 1 позиция из 100); основной расход почты — позиции без цен на сайтах.
- Headless (Chrome, сервер 7 ГБ) — только для помеченных сайтов, 1–2 воркера.

## 7. API (черновик)
- Заявки: поле `price_mode` (`rfq` по умолчанию | `lite` | `hybrid`) в `POST /submissions`.
- Мониторинг: `POST /monitoring/programs`; `POST /monitoring/programs/{id}/items` (upsert, 202 + `import_id`); `GET /monitoring/programs/{id}` (покрытие, свежесть, расход); `GET /monitoring/programs/{id}/prices?updated_since=&cursor=` (изменения курсором); `GET …/items/{client_ref}` (источники, история).
- Вебхуки с HMAC: `price.changed`, `item.found`, `item.not_found`, `program.coverage`.
LazyLift — первый потребитель: вместо потока мелких заявок — программа мониторинга каталога.

## 8. Уроки CE и LazyLift → обязательные правила
1. Доставка/МКАД/порог заказа — не цена; цитату-доказательство храним.
2. Артикул — по токену, с переводом похожих букв; не подстрокой.
3. Бренд при явном расхождении — отказ.
4. Серая зона сопоставления — только через LLM-проверку; аналог ≠ наш товар.
5. Единица цены и НДС — обязательные поля; неизвестно = null.
6. Нет цены сейчас — старую не держим.
7. Сбои пишем; мягкий 404 ловим.
8. Скачок — повтор через 1–2 дня.
9. Выбросы — флаг в БД; для 1–3 цен — сверка с КП-историей.
10. Учёт стоимости LLM — по точному имени модели; поиск тоже учитываем.
11. Повторный LLM-разбор недетерминирован: проверенный результат не перезаписываем без причины.
12. Ответ поставщика сопоставляем только с позициями этого письма.
13. Письма — только дробные (1–4 позиции); большой список одному поставщику не шлём.

## 9. Фазы
- **Ф0. Фундамент**: схема, приём номенклатуры, канонические товары, регулятор бюджетов, перенос загрузчика/извлечения/монитора из CE с правками §8.
- **Ф1. Lite на пилоте** (выборка каталога LazyLift): поиск, листинги, переобход, выдача курсором. Метрики: покрытие, точность сопоставления (ручная выборка), стоимость/позицию.
- **Ф2. Профили сайтов**: поиск по сайту, sitemap → меньше Яндекса.
- **Ф3. Гибрид**: `mp_asks` в план дня v2, проверочный шаблон, сверки, уровни доверия и частота выборки; сверка КП из обычных заявок.
- **Ф4. API/вебхуки/кабинет/биллинг**; `price_mode` для заявок.

## 10. Риски
- **Качество сопоставления** на 30 тыс. позиций — главный риск (LazyLift: 95% ошибок в серой зоне). Без выборочного ручного контроля не запускать.
- **Почтовая ёмкость**: Гибрид и мониторинг конкурируют с заявками за ящики и капы — регулирует общий план дня.
- **Антибот/JS-цены**: headless дорог по памяти; закрытые сайты — в почтовый канал.
- **Диск** app-сервера (свободно 11 ГБ): сырые страницы не храним.

## 11. Решения владельца
- (2026-10-14) Режимы получения цены: **Основной** (КП почтой), **Lite** (сайты), **Гибрид** (сайты + выборочная проверка КП, доверие к сайту, почта для остальных). Тип задачи: **Заявка** (закрывается) и **Мониторинг** (регулярно, 10–90 дней). Текущий алгоритм — Основной режим, остаётся.
- (2026-10-14) Проверка доверия — **дробными запросами КП** на выборку позиций, найденных на сайте; **чем выше доверие — тем реже** (1 из 10 → 1 из 50 → 1 из 100). Письма со 100+ позициями не шлём.
- (2026-10-14) Варианты, которые поставщик может заявить: «все цены актуальны», «актуально наличие», «актуальны цены только на товары в наличии» — учитываются как **область доверия**, уровень определяют сверки.
- (2026-10-14) Движок — **модуль внутри IQOT** (таблицы в БД `iqot`), код CE переносится с правками §8.
- (2026-10-14) Пилот — **выборка каталога LazyLift** (3–5 тыс. ходовых позиций).
- (2026-10-14) Обход — вежливый (robots.txt, лимит на домен), **UA браузера**; капчи не обходим.
- (2026-10-14) **Маркетплейсы и агрегаторы игнорируем.**
