# IQOT Public API v1 — изменения

Полное описание методов: [IQOT_API_Reference.md](./IQOT_API_Reference.md) · подключение Гибрида: [Monitoring_Hybrid_Guide.md](./Monitoring_Hybrid_Guide.md) · OpenAPI: [openapi.yaml](./openapi.yaml)

Все изменения ниже — в рамках `/v1/`. Существующие поля не удалялись и не переименовывались. Добавлены:

- новые необязательные поля запросов;
- новые поля ответов;
- новые значения перечислений;
- в мониторинге — несколько полей, которые теперь могут быть `null` (отмечены ⚠).

Неизвестные поля и значения перечислений ваша интеграция должна игнорировать.

**Сводка: что проверить в интеграции**

| # | Изменение | Действие |
|---|---|---|
| 1 | `oem_articles` в загрузке позиций мониторинга | Передавайте все OEM-номера позиции, если их несколько |
| 2 | Позиции видны только страницы с её артикулами | Ничего, кроме пункта 1. Часть ранее показанных источников исчезнет из выдачи — это исправление ошибочных сопоставлений |
| 3 | ⚠ Источник цены `source_type: "kp"` с `url: null`, `price: null` | Не рассчитывайте, что `url` и `price` источника всегда заполнены; цена КП — в `kp.price` |
| 4 | Сводка цен учитывает КП | Если строите свою сводку, берите `price ?? kp.price` |
| 5 | `best_price.price_source`, `plan.kp_price_multiplier` | Новые поля — по желанию |
| 6 | CSV: колонка `web_price` теперь реальный признак | Если фильтровали строки CSV по `web_price = 1`, проверьте логику |
| 7 | `client_category` в позициях мониторинга | Рекомендуется передавать, особенно для режима `hybrid` |
| 8 | Заявки: доступный баланс учитывает резервы, новые причины отклонения | Обработайте `moderation_timeout`, `deadline_expired`, поле `held` в ошибке 402 |
| 9 | Мониторинг: начисление за покрытые позиции, блок `billing`, `paused_reason: billing` | Следите за `billing.warning` — пополните баланс до даты паузы |

## 16.10.2026 — мониторинг: начисление за покрытые позиции

С 15.10.2026 мониторинг тарифицируется по плану (§10.12 справочника): начисление ежедневно, списание с баланса раз в 7 дней и в конце периода подписки. В объекте программы — блок `billing` (начислено и не списано, последнее списание, предупреждение о нехватке средств) и поле `paused_reason`. При нехватке средств — предупреждение в `billing.warning`, через 3 дня — пауза программы (`paused_reason: billing`), снимается автоматически после пополнения.

## 16.10.2026 — мониторинг: идентичность позиции

### Новое: несколько OEM-артикулов у позиции — `oem_articles`

`POST /monitoring/programs/{id}/items` принимает в каждой позиции необязательное поле `oem_articles` — массив строк, до 20 элементов, каждая до 255 символов. Передавайте в нём все кросс-номера позиции:

```json
{
  "client_ref": "M02502",
  "name": "Ремень тахометра D4*600",
  "brand": "KONE",
  "article": "KM247024",
  "oem_articles": ["KM247024", "KM85869H01", "PC-04L=600"],
  "client_category": { "code": "cat-114", "path": ["Лифты", "Главный привод", "Тахометры"] }
}
```

- Поле `article` остаётся. Если передать оба поля, коды позиции — их объединение. Повторы допустимы.
- Изменение `oem_articles` при повторной загрузке с тем же `client_ref` запускает повторное сопоставление позиции, как и изменение `article`.
- Поле `oem_articles` возвращается в `GET …/items` и в карточке `GET …/items/{client_ref}`. Если артикулов нет — пустой массив.

### Изменено: позиции показываются только страницы с её артикулами

Раньше позиция могла получить страницы **другого варианта** того же товара. Так бывало, когда у поставщиков разные варианты (длина, исполнение, левое/правое) числятся под общими кросс-номерами. Пример: позиция «Ремень тахометра D4×600, KM247024» получала страницы ремня D4×550 (FI264123) и D4×650 (FI264124).

Теперь действует правило:

- позиция видит страницу поставщика, только если на ней найден хотя бы один артикул позиции (`article` или `oem_articles`) — в адресе, заголовке, описании или в SKU разметки;
- страница, где указан только чужой кросс-номер, в выдачу этой позиции не попадает.

Правило применяется во всех местах:

- `GET …/prices`, `GET …/items/{client_ref}`, `GET …/export`;
- покрытие программы (`items.covered`, `last_priced_at`);
- письма поставщикам в режиме `hybrid`: они формируются с названием и артикулом вашей позиции.

Что заметит интеграция:

- У части позиций уменьшится число источников (`sources`) — ушли страницы других вариантов. Эти позиции попадут в инкрементальную выгрузку `GET …/prices?updated_since=…`.
- В карточке позиции `product.identifiers` теперь содержит только артикулы этой позиции, без кросс-номеров, которые к товару добавили другие клиенты.
- **Передавайте все OEM-номера позиции** в `oem_articles`. Страница, на которой указан только кросс-номер, не переданный вами, не будет показана.

### Исправлено: отметка «подозрительно» (`status: "suspicious"`)

Резкий отрыв цены теперь считается **по ценам самой позиции** — по тем источникам, которые она видит. Раньше правильная цена могла получить `suspicious` на фоне цен других вариантов: 725 ₽ за D4×600 рядом с 5 000 ₽ за другие длины.

Правила:

- от 4 цен — отрыв от медианы больше чем в 4 раза;
- **3 цены — отрыв от медианы больше чем в 10 раз** (новое: раньше при трёх ценах явные ошибки вроде 32 810 ₽ рядом с 550 и 725 ₽ не отсекались);
- 1–2 цены — не оцениваются.

Источник со `status: "suspicious"` в сводку (`summary`, `best_price`) не входит. Отметка «скачок цены» (резкое изменение цены страницы между проверками) снимается после повторной проверки через 1–2 дня.

## 15.10.2026 — мониторинг: режим «Гибрид» и КП поставщиков

### Новое: цены из КП поставщиков в выдаче

В режиме `hybrid` IQOT запрашивает коммерческие предложения в трёх случаях:

1. у поставщиков, на сайте которых товар есть, но цена «по запросу»;
2. у профильных поставщиков, если у позиции меньше трёх цен;
3. проверочно — по ценам сайтов.

Полученные КП отдаются в источниках цен (`sources[]`):

| Случай | Как выглядит источник |
|---|---|
| КП по странице сайта (в том числе «цена по запросу») | `source_type: "site"`, `url` — страница товара, `price` — цена сайта или `null`, `kp: { price, currency, vat_included, received_at }`, `flags.kp: true` |
| КП поставщика без страницы товара | `source_type: "kp"`, `url: null`, `price: null`, цена — в `kp.price`, `supplier_domain` — домен поставщика (может быть `null`), `site_trust_level: null` |

**Новые и изменённые поля источника (`MonitoringPriceSource`):**

| Поле | Изменение |
|---|---|
| `source_type` | **Новое.** `site` или `kp` |
| `url` | ⚠ Может быть `null` (для `source_type: "kp"`) |
| `supplier_domain` | ⚠ Может быть `null` (поставщик без сайта и с почтой на бесплатном домене) |
| `site_trust_level` | ⚠ Может быть `null` (для `source_type: "kp"`) |
| `kp` | Заполняется и для КП по страницам «цена по запросу» |
| `history[].source` | Для КП — `kp` |

### Изменено: сводка цен учитывает КП

`summary` (`best_price`, `min`, `median`, `max`, `sources_priced`) считается по «цене источника»: это цена сайта, а если её нет — цена КП. Раньше КП в сводку не входили.

В `best_price` добавлено поле **`price_source`**: `web` (цена сайта) или `kp` (цена КП). Поля `best_price.url` и `best_price.supplier_domain` могут быть `null`, если лучшая цена — КП без страницы.

### Изменено: инкрементальная выгрузка

Позиция попадает в `GET …/prices?updated_since=…` не только при изменении цены на сайте, но и когда:

- пришло КП;
- поставщик подтвердил цену сайта по почте (`flags.email_confirmed`).

### Изменено: CSV-выгрузка `GET …/export`

- В выгрузку входят источники с ценой сайта **или** с КП. Раньше — только с ценой сайта.
- Колонка `web_price` теперь показывает реальный признак (`1` — цена с сайта, `0` — только КП). Раньше в ней всегда была `1`.

### Новое: множитель ставки за позицию с КП — `plan.kp_price_multiplier`

В объекте программы (`GET /monitoring/programs/{id}` и др.) в `plan` добавлено поле `kp_price_multiplier` (сейчас 3).

Позиция, по которой есть свежее КП поставщика (не старше 60 дней), тарифицируется по ставке `price_per_item × kp_price_multiplier`, даже если у неё есть и цены с сайтов. Позиции только с ценами сайтов — по обычной ставке.

### Новое: категория заказчика в позициях мониторинга — `client_category`

`POST …/items` принимает `client_category` в том же формате, что заявки: `{ "code": "...", "path": [...], "metadata": {...} }`. По категории IQOT определяет тип товара и подбирает профильных поставщиков. Для режима `hybrid` это нужно, чтобы запросы КП уходили профильным поставщикам. Соответствие категорий общее с заявками `/submissions`.

### Новое: методы мониторинга

| Метод | Назначение |
|---|---|
| `GET /monitoring/programs` | Список программ клиента |
| `GET /monitoring/programs/{id}/items/{client_ref}` | Карточка позиции: сопоставленный товар, сводка, источники, история цен (`history_days`, по умолчанию 90) |
| `DELETE /monitoring/programs/{id}/items/{client_ref}` | Снять позицию с мониторинга |
| `GET /monitoring/programs/{id}/export` | Вся программа в CSV (UTF-8 с BOM, `;`), не чаще 6 раз в минуту |

### Изменено: поиск без потолка на программу

Скорость первичного поиска больше не ограничивается на уровне программы — её задаёт общая загрузка сервиса. Большие каталоги (10–30 тыс. позиций) обрабатываются быстрее. Изменений в запросах нет.

## 14.10.2026 — заявки: резервы и сроки

### Изменено: доступный баланс учитывает уже зарезервированное

При `POST /submissions` доступная сумма считается так: баланс − активные резервы + разрешённый овердрафт. В ошибке `402 insufficient_balance` в `details` добавлено поле **`held`** (сумма активных резервов) — рядом с `required_hold`, `balance`, `overdraft_percent`.

### Новое: причины отклонения позиций

| Код | Когда | Можно повторить |
|---|---|---|
| `moderation_timeout` | Позиция не разобрана модерацией за 24 часа, тип товара не определён | да |
| `deadline_expired` | Срок сбора (`deadline`) истёк до рассылки позиции | да |

Если тип товара определён, позиция, не разобранная за 24 часа, теперь **принимается автоматически**.

### Изменено: жизненный цикл резерва

- Резерв снимается, когда истёк срок сбора без минимума КП. Срок — `deadline` заявки, а если он не задан, 30 дней с начала рассылки.
- Если минимум (3 КП) набран **позже**, в течение 90 дней, сумма списывается постфактум. Баланс может уйти в овердрафт — смотрите заголовок `X-Balance-Warning`.
- Принятые позиции уходят в рассылку сразу, не дожидаясь модерации остальных позиций заявки.
